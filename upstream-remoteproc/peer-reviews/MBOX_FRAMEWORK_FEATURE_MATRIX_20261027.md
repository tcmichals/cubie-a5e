## Core code paths verified

- `mbox_controller_register()`: no of_xlate/fw_xlate -> `fw_mbox_index_xlate()`, which rejects
  `nargs < 1` and `args[0] >= num_chans`. Our 12-channel default xlate is bounds-checked.
- `__mbox_bind_client()`: sets `chan->cl` before `startup()`; on startup failure calls
  `mbox_free_channel()`, i.e. **our shutdown() runs after a failed startup()** (we handle it via
  `tx_irq_held`).
- `mbox_free_channel()`: `shutdown()` first, then `cl = NULL`, `active_req = MBOX_NO_MSG`;
  `msg_count` is not reset. Our shutdown's `synchronize_irq()`/`free_irq()` makes sure no
  `mbox_chan_txdone()`/`received_data()` runs after `cl` is cleared (tx_tick -> msg_submit
  dereferences `chan->cl->tx_prepare` if messages are still queued).
- `msg_submit()`: on `send_data() != 0` the message stays queued, `active_req` stays NO_MSG and,
  in poll mode, the hrtimer is not kicked; `txdone_hrtimer()` only polls channels with
  `active_req != MBOX_NO_MSG`. So in poll mode an -EBUSY would stall until the next
  `mbox_send_message()` -> our "hold the message, return 0" is required, not a quirk.
- IRQ mode -EBUSY: armed write IRQ -> `mbox_chan_txdone()` -> `tx_tick()` with active_req NO_MSG
  -> `msg_submit()` resends, no client callback. Same as omap-mailbox `omap_mbox_chan_send()`.
- `mbox_send_message()` with `tx_block` and timeout: `tx_tick(chan, -ETIME)` clears active_req
  but cannot tell the controller.
- `mbox_flush()`: only effect when ops->flush exists; in-tree callers: tegra-tcu, mediatek drm.
- `mbox_client_peek_data()`: only caller in tree: drivers/dma/bcm-sba-raid.c.
- `mbox_controller_unregister()` (devm, runs first on unbind): frees every bound channel
  (shutdown), then `hrtimer_cancel` if poll. devm order afterwards: RX irq freed, reset put,
  clocks disabled, iounmap. Correct order.

## Classification of features we do not use (or use differently)

### NEEDED
None found. Every framework hook our hardware/clients need is implemented and the core paths
above behave correctly with the driver as written.

### RECOMMENDED
R1. Poll mode: stale held message after a client tx_block timeout (we use `last_tx_done`
    differently from the idiom: it writes the held message). Scenario: client with
    `tx_block=true, tx_tout=N` sends while FIFO full -> send_data() holds msg (tx_held bit) and
    returns 0 -> remote stalls, core times out and `tx_tick(-ETIME)` -> next send finds room,
    writes the new message directly -> the next `last_tx_done()` sees tx_held still set and
    writes the old message after the new one (out-of-order/extra kick). Not reachable with
    sunxi_rproc (`tx_block=false`, static const payload) and harmless for doorbells, but a
    generic client could hit it. Fix: in send_data()'s "room" path, `clear_bit(n, &tx_held)`
    (or write the held one first). Also be ready to justify the deviation from the core
    contract ("only in polling mode send_data returns -EBUSY", last_tx_done is a query) in the
    commit message with the msg_submit()/txdone_hrtimer() reasoning above; no other in-tree
    driver does work in last_tx_done().
R2. (Low, reviewer-prompt only) IRQ mode returns -EBUSY from send_data although the core doc
    says only poll mode should; precedent omap-mailbox (`omap_mbox_chan_send()`), path verified
    above. No change, cite omap in the commit message. Touches DECISION "TX completion: timer or ISR".

### NOT APPLICABLE / no change
- ops.flush (3: mtk-cmdq, sprd, tegra-hsp): only callers are tegra-tcu console and mtk drm;
  sunxi_rproc never calls mbox_flush(). mbox_flush() returns -ENOTSUPP cleanly without it.
  Add only if an atomic console/panic client appears.
- of_xlate (23) / fw_xlate (1): drivers using it have multi-cell specifiers or sparse/typed
  channels (ti-msgmgr, imx, tegra-hsp, qcom-ipcc, omap by name). Our `#mbox-cells = <1>` dense
  index is exactly what `fw_mbox_index_xlate()` handles, with bounds checks. Same as sun6i-msgbox.
- System sleep PM (7: imx, th1520, cmdq, omap, qcom-ipcc, stm32-ipcc, ti-msgmgr; noirq 4):
  they restore IRQ masks lost when the block powers down. On sun55i: dtsi uses PSCI with no
  suspend states, sunxi-ng sun55i CCU has no suspend/resume either, so only s2idle exists and
  registers are retained; a level RX IRQ pending across s2idle is replayed on resume.
  sun6i-msgbox has none. Revisit (save/restore READ_IRQ_ENABLE + write threshold, or re-run
  startup in resume_noirq like tegra-hsp) only if A523 gains suspend-to-RAM.
- Runtime PM (3): DECISION (D12 / Unbind: all bank clocks stay on, resets never asserted).
- Wakeup / IRQF_NO_SUSPEND / dev_pm_set_wake_irq (10/9): needed only if a remote must wake
  Linux from sleep; no such requirement. Would be a new owner decision.
- IRQF_SHARED (11): our lines are dedicated (binding: one line per bank). IRQF_ONESHOT/threaded
  (11/10): used where the RX path sleeps or reads long messages; our handler is atomic and
  bounded (12 x <=8 reads); on PREEMPT_RT the handler is force-threaded anyway. IRQF_NO_AUTOEN:
  0 users; not needed since enables are cleared before devm_request_irq().
- .remove (12): needed by drivers with non-devm resources; ours are all devm and the teardown
  order is correct (above). sun6i needs .remove only because it uses the non-devm register.
- platform .shutdown (1, bcm74110): kexec/reboot leftover state is cleared at probe instead
  (read enables, status, our write enables).
- suppress_bind_attrs (1, qcom-ipcc): sysfs unbind while sunxi_rproc holds channel 9 leaves the
  client with a pointer into devm-freed `chans` (UAF on next kick/free). Framework-wide issue
  shared by all 42 other drivers; unbind behaviour is an owner DECISION (2026-10-27, Unbind).
  Mention only if the owner wants to forbid unbind.
- MODULE_ALIAS (4): redundant with MODULE_DEVICE_TABLE(of) (39, ours included).
- of_device_get_match_data (15): single compatible; route table is static. Becomes relevant
  with the A733 variant (DECISION: A733 placeholders).
- readl_relaxed (14): ours must stay non-relaxed: writel's barrier orders vring writes before
  the doorbell. sun6i also uses readl/writel. Endian accessors (4): little-endian block, n/a.
- readx_poll_timeout (4): used by flush/blocking-TX drivers; we never busy-wait.
- debugfs (2): n/a. Kconfig: `depends on ARCH_SUNXI || COMPILE_TEST` matches sun6i; sun6i also
  has `default ARCH_SUNXI` (9/43 entries have a default) - optional, maintainers usually prefer
  no default for new drivers.
- platform_get_irq_byname / ioremap_resource_byname (6/2): we index by position; binding
  defines names in the same order; index use is the majority idiom.
- peek_data (7): our implementation (FIFO count > 0, no delivery) matches sun6i/altera/ti-msgmgr;
  flexrm/mpxy deliver from peek. Core doc allows both; only caller is bcm-sba-raid.
- last_tx_done provided while txdone_irq: harmless (hi6220, mhuv2/v3 do the same; core never
  calls it in IRQ mode).
- RX ack order: core says ack RX after `mbox_chan_received_data()` returns; we pop the FIFO and
  clear pending before delivery (outside the lock). For a FIFO the pop is the read; the pending
  bit re-sets if a message arrives after the clear (level). sun6i pops before delivering too.
  Different idiom (12 enable&status read pairs per IRQ vs sun6i one status read), correct.
